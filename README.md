# Image Upload Feedback Analytics Dashboard

A self-updating dashboard that tracks user feedback and model-quality trends
for an **Image Upload** feature, built the way a **Copilot Feedback
Analytics**-style team would track it: sentiment split, feedback volume,
recognition accuracy, resolution time, and the top drivers of negative
feedback.

**Live example of what it looks like once deployed:** `https://<your-username>.github.io/<repo-name>/`
(GitHub Pages URL, set up in step 4 below.)

All data in this repo is **synthetic** — generated by a script, not pulled
from a real product — so it's safe to publish publicly while still showing
real analytical work.

---

## Why this project (for a Business Analyst interview)

This is built to demonstrate the parts of the BA toolkit that come up most
in an interview loop like Amazon's:

- **Defining metrics that matter** — positive/negative feedback rate,
  recognition accuracy trend, resolution-time SLA, feedback-by-category —
  not just "a chart of everything."
- **SQL** — [`sql/analysis_queries.sql`](sql/analysis_queries.sql) has
  window functions, rate calculations, and cohort/bucket analysis written
  against the same dataset the dashboard uses.
- **Turning data into a decision-ready story** — the dashboard's "top
  negative-feedback drivers" panel is deliberately the thing a PM or eng
  lead would look at first to decide what to fix next.
- **Data pipeline thinking** — the dataset isn't static; it's designed to
  be refreshed on a schedule, like a real reporting pipeline would be.
- **Communicating trade-offs** — see [`docs/talking_points.md`](docs/talking_points.md)
  for how to walk an interviewer through the design decisions out loud.

### Metrics tracked

| Metric | What it shows |
|---|---|
| Total feedback volume | Overall engagement with the feedback mechanism |
| Positive / negative / neutral rate | Core sentiment split, trended daily |
| Avg. recognition accuracy | Proxy for image-recognition model quality |
| Avg. resolution time | How fast reported issues get resolved |
| Feedback by category | Blurry detection, false positives, missed objects, wrong labels, duplicates, slow processing, failed uploads |
| Feedback by region | NA / EU / APAC / LATAM split |
| Top negative-feedback drivers | Ranked categories to prioritize fixing |

## Running it locally

The dashboard is a static page that `fetch()`s a JSON file, so it needs to
be served over HTTP (not opened as a bare `file://` path, which browsers
block from fetching local files).

```bash
git clone https://github.com/<your-username>/<repo-name>.git
cd <repo-name>
python3 -m http.server 8000
# then open http://localhost:8000
```

## Regenerating / extending the dataset

```bash
python3 data/generate_daily_data.py
```

This is idempotent — it fills in any missing days up to today and keeps a
rolling 120-day window, so running it repeatedly won't duplicate data. Run
it with `--as-of YYYY-MM-DD` to simulate a specific date, which is useful
for demos.

## How the "daily automated update" works

1. **`update-data.yml`** runs on a daily GitHub Actions schedule (and can
   be triggered manually from the Actions tab). It calls
   `generate_daily_data.py`, which appends the new day and drops the
   oldest one, then commits `data/feedback_data.json` and `.csv` back to
   `main` if anything changed.
2. **`deploy-pages.yml`** redeploys the static site to GitHub Pages on
   every push to `main` — including the commit from step 1.
3. Net effect: **no manual step** is needed to keep the live dashboard
   current. Opening the Pages URL any day shows data through "yesterday."

In a real (non-dummy) setup, step 1 would instead be a job that pulls from
your actual feedback store (e.g. a nightly export from Redshift/S3, or a
call to an internal feedback API) and writes it into the same
`feedback_data.json` shape — the dashboard code wouldn't need to change.

## Setting this up in your own GitHub account

1. Create a new empty repo on GitHub (no README/license, so there's no
   merge conflict with these files).
2. From this folder:
   ```bash
   git init
   git add .
   git commit -m "Initial commit: image upload feedback analytics dashboard"
   git branch -M main
   git remote add origin https://github.com/<your-username>/<repo-name>.git
   git push -u origin main
   ```
3. In the repo's **Settings → Pages**, set **Source** to "GitHub Actions"
   (the included `deploy-pages.yml` handles the rest).
4. In **Settings → Actions → General → Workflow permissions**, make sure
   "Read and write permissions" is enabled so `update-data.yml` can commit
   the daily refresh.
5. Optional: in the **Actions** tab, run `update-data.yml` manually once to
   confirm it works before waiting for the schedule.

## Notes on the data

All records are synthetic, generated with a seeded random model
(`data/generate_daily_data.py`) so results are reproducible per date. It
simulates: weekday vs. weekend upload volume, a mild upward accuracy trend
over time, and category-specific tendencies toward positive/negative
sentiment (e.g., "upload failed / crashed" skews strongly negative;
"correct result" skews strongly positive). It is meant to be *directionally
realistic* for demo purposes, not to represent any real product's numbers.
